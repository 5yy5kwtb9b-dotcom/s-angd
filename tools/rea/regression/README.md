# REA 的 123 条 Codex 对话回归测试

从 s-angd 仓库根目录运行。每条用例启动一个独立的 Codex app-server，创建一个全新的临时对话。唯一一条用户消息取自总清单对应的文本框，保留换行。需要解压文件、启动样例或准备前序证据的操作，由 Codex 在同一轮里按原文执行。[中文总清单](../123条零报错指令中文总清单.md) · [样例与会话准备](../Codex样例与会话准备.md) · [人工验收记录](../123条总清单逐条验收.md)

## 运行

使用已登录 Codex CLI、配置好 `rea` 和 `mac_pcap` 的 Mac。脚本使用 Python 3.9 或更高版本的标准库。保持 REA、Wireshark、Ghidra 和样例所需的浏览器等本机依赖可用。本机验证环境使用 Codex CLI 0.169.1 和 REA 6.9.0。

**先检查基线**。这个命令离线核对总清单的 123 条文本、历史验收记录中的 SHA-256、测试包指纹以及断言的覆盖情况。输出每条的编号、服务、工具名和指令指纹。

```sh
python3 tools/rea/regression/run.py --list
```

**抽测三类用法**。第 1 条直接查询 Mac 替代工具，第 5 条读取 HAR 文件，第 57 条先建立 Ghidra 会话。

```sh
python3 tools/rea/regression/run.py --ids 1,5,57 --output "$HOME/rea-regression-runs"
```

**全量回归**。默认跑 1–123，包含 15 条直接用、50 条需要文件、58 条需要会话或前序结果的指令。第 1–3 条使用 `mac_pcap`，其余 120 条使用 `rea`。以下命令最多并行 5 个独立对话。省略 `--jobs` 时逐个运行。一次全量运行会实际发起 123 轮模型请求，耗时和用量随本机依赖和账号情况变化。

```sh
python3 tools/rea/regression/run.py --jobs 5 --output "$HOME/rea-regression-runs"
```

**复测指定编号**。从报告中的 `failed_ids` 取得编号，多个编号用逗号分隔，也可用区间。每次调用都生成新的运行目录，重跑同一条也会开新对话。单条模型轮次默认等待 900 秒，可用 `--timeout` 调整。

```sh
python3 tools/rea/regression/run.py --ids 5,54-58 --output "$HOME/rea-regression-runs"
```

## 怎样判定通过

每条都必须同时满足以下条件。

- Codex 报告该轮已完成，有最终答复。事件流中只有一条用户消息，其文本与清单原文完全一致。
- 目标服务的目标工具确实产生了结果。从准备到最终回答，整轮所有已记录的 MCP 调用均成功。中途报错后自行重试成功，仍计为失败。
- 目标工具的成功返回满足该编号的全部断言。同一条指令可以按原文多次调用目标工具，例如第 34 条分别核对默认表和中文资源表。断言使用工具返回的数据。[逐条断言](./checks.tsv)
- 整批结束时核对已创建的对话 ID 是否唯一。退出码 `0` 表示选中用例全部通过，`1` 表示回归失败，`2` 表示参数、输入文件或基线有误，`130` 表示用 Ctrl-C 中断。

断言选取样例中可复核的事实。第 2 条核对两帧的帧号与 60、74 字节的帧长，第 20 条检查源码映射中是否含有 `main.ts`。依赖本机状态的项目按结果结构或必要字段检查，例如第 36 条要求 ADB 返回设备列表，设备数可随环境变化。每条报告同时保存最终答复和历史人工观察结果，便于复核断言以外的细节。

## 查看报告

`--output` 指定**父目录**。每轮都会打印实际运行目录，省略该参数时使用系统临时目录。需要长期保存的记录请指定持久目录。

| 文件 | 内容 |
|---|---|
| `plan.json` | 本轮选中的编号、脚本、总清单、样例包和断言文件的 SHA-256 |
| `summary.json` | 已执行数、通过数、失败编号、中断时未执行的编号、MCP 调用与报错次数，以及对话唯一性 |
| `005/result.json` 等 | 该条原文与指纹、thread/turn ID、用户消息核对、实际调用顺序、报错原因、各断言命中情况、最终答复和历史参考结果 |
| `005/target-results.json` 等 | 有目标工具成功返回而用例失败时，保留目标工具的结果，供核对字段、摘要与完整视图 |
| `005/server.log` 等 | 对应 app-server 的标准错误输出，可用于诊断启动、连接及协议问题 |
| `005/s-angd/` 等 | 该条独立的工作目录，预置两份清单与样例 ZIP，保留对话实际写入此目录的产物 |

出现失败时，先打开对应 `result.json`。看 `error` 和 `turn_status` 定位启动、权限、连接或超时问题，看 `calls` 中的 `ok: false` 定位 MCP 报错，看 `checks` 中的 `matched: false` 定位样例结果的差异。临时对话采用工作区写入沙箱及 Codex 自身的审批机制。需要额外交互时，该条记录为失败，脚本不会代替用户回答。各条独立使用自己的目录和 REA 会话，本机安装的依赖可以复用。

## 维护

指令正文以[总清单](../123条零报错指令中文总清单.md)为源，运行前逐条与[已验收的最终指令及指纹](../123条总清单逐条验收.json)比对。修改指令后，先在新对话验收，再同步更新这两处基线。更新样例 ZIP 时，应重新核对受影响的返回值，再更新脚本中的包指纹与对应断言。

`checks.tsv` 每行四列，依次为编号、结果路径、断言和 JSON 期望值，使用制表符分隔。路径相对于工具的 `normalized_result`、`result` 或直接返回体，点号访问字段或列表下标，单独的 `.` 表示整个值。等价的摘要和完整视图路径可用竖线分隔。`eq` 核对类型和值，`contains` 在指定子树的字符串值中查找文本，`length` 检查列表长度，`list` 检查列表类型，`nonempty` 检查非空字符串或集合，`positive` 检查正数。后三种类型或范围断言的第四列统一写 `true`。
